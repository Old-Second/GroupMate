主人诊断命令读出运行状态、累计指标和按群按人的用量。这些命令只回文本，不改变任何运行行为，也不触发模型调用。

## 命令

四条命令都只对机器人主人开放，私聊和群里都能用。

| 命令 | 作用 |
| --- | --- |
| `#GroupMate状态` | 并发、内存、累计运行结果、Token、报价与费用摘要，以及最近若干个运行引用 |
| `#GroupMate指标` | 计数器与耗时分位（计数最多展开 40 条，其余只报条数），加观测管道每个 sink 的接受、丢弃、失败和隔离数 |
| `#GroupMate用量` | 按计费日、按群、按人的 Token 与参考费用（按群和按人各最多展开 16 行，其余只报条数） |
| `#GroupMate诊断 <32 位小写十六进制>` | 回放指定运行的脱敏轨迹；runRef 从 `#GroupMate状态` 的最近轨迹里取 |

`#GroupMate诊断` 要求该运行的轨迹仍被保留。基础级别只保留失败、取消、呈现异常和按采样率抽中的成功运行，所以多数成功运行查不到；想保留全部要把可观测性切到诊断级别。

## 计数窗口

可观测性开启时，`#GroupMate状态` 和 `#GroupMate指标` 都带一行计数窗口：

```
计数窗口：2026-10-29T03:00:00.000Z 起（重置 2 次）
```

计数器和耗时只在内存里，进程重启即清零；把可观测性切到完全关闭也会清空全部事实并重开窗口。重置次数让这件事可见——否则「自某时刻起累计」的口径会在关一次又开一次之后静默变化，而数字看上去仍然连续。

指标没有做持久化，这是刻意的：宿主内存余量只有约 1 MiB 量级，而把每次计数都写进 Redis 会把观测从「失败也不影响业务」变成「写放大影响业务」。需要跨重启的历史用落盘内容日志。

## 报价过期

费用用「已上报的 Token 计数 × 请求时冻结的价格表」算出，和账户实际扣费是两件事，所以每一处都标明是参考值或上界，而不是账单。

价格目录有硬编码的复核日期。过了那个日期，所有报价解析为空，费用整体退化为「不可用」。`groupmate.agent.model_price` 计数器把这件事变成可数的事实：

```
报价：available 15 / missing_or_expired 2
```

`missing_or_expired` 持续增长且费用变成不可用时，先看价格目录的复核日期是否已过，而不是去找模型配置。

## 用量聚合的身份边界

按群和按人汇总必然要用到群号和 QQ 号。这些标识只以下面的方式存在：

- **只在内存窗口里。** 最多保留 7 天，每天最多 32 个群和 64 个人，超出的只累加溢出次数，不挤掉已有条目。不落盘、不写 Redis、不进脱敏轨迹。
- **展示另有行上限。** 按群和按人各最多展开 16 行（跨全部保留日，按 Token 降序），其余报成「其余 N 行未展开」。这和「维度溢出」是两件事：溢出是没进窗口，未展开是进了窗口但这次没打印。
- **不作为指标标签。** 指标保持固定的低基数仪表，QQ 号、群名和自由文本都不能当标签值；聚合是独立结构，不是指标的一个维度。
- **展示时只给掩码尾号。** `****1012` 这样的形式。两行掩码相同代表两个不同的群或人，不是重复行。
- **关闭即清空。** 把「按群与按人用量聚合」关掉，或把可观测性切到完全关闭，窗口立即清零。

`#长期记忆 删除全部` 不清这个窗口，和它不清落盘日志是同一个道理：诊断系统独立于记忆的遗忘流程。要清掉它，关闭聚合开关或重启进程。

按天用的是北京时间，和模型的峰谷计费日对齐，所以一天的边界落在 UTC 16:00。

累计行覆盖窗口开启以来的全部运行，包括已经滚出 7 天的那些，所以它通常大于按天各行之和。

## 配置

锅巴「网络与调试」分组：

| 字段 | 默认 | 说明 |
| --- | --- | --- |
| 可观测性级别（`observabilityLevel`） | 基础 | 关闭时不采集任何运行事实并清理已保留轨迹 |
| 成功轨迹采样率（`observationSuccessSampleRate`） | 5 | 成功运行保留轨迹的百分比，0-100 |
| 按群与按人用量聚合（`usageAggregationEnabled`） | 开启 | 关闭后 `#GroupMate用量` 只回提示，窗口清空 |

采样率在运行开始时冻结进该运行的观测策略，并随检查点一起保存。校验用的是检查点里记录的那个采样率，所以改配置不会让已有检查点失效；改动只影响新发起的运行。采样率调高只增加保留的成功样本，失败和取消的运行一直全保留。

默认开启用量聚合的理由：完整身份本来就写进了默认开启的落盘内容日志，内存窗口加掩码展示的暴露面严格小于它；而关闭它会让「哪个群哪个人用掉多少」重新变成查不到。

## 为什么没有 Prometheus 或 OpenTelemetry 导出

评估结论是暂不实现，依据有三条：

1. **常驻端点要新开一个鉴权面。** Prometheus 抓取需要一个长期监听的 HTTP 端点。本项目的 Web 管理面刚做过一轮边界审计，再加一个默认监听的端点等于新增一处需要同等对待的入口，而它服务的只有主人一个读者。
2. **SDK 体积换不回信息量。** OpenTelemetry 的 Node SDK 及其依赖在低内存宿主上不划算，而它能导出的恰好就是现在 `#GroupMate指标` 已经读得到的那 15 个仪表。
3. **缺的是读取路径，不是传输协议。** 原本的问题是 8 个计数器和 2 个直方图没有任何读取者，补上命令就已经解决；聚合维度的缺口也来自仪表没有身份维度，换个传输协议并不会补上它。

真要接外部监控时，接入点是 `MetricsRegistry.snapshot()`：它返回的结构已经是解析过、冻结的定值，写一个导出器不需要改仪表定义。
